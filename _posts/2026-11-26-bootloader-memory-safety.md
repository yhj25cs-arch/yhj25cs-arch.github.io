## 1. 논문 소개 및 선정 이유

- **논문 제목:** A Comprehensive Memory Safety Analysis of Bootloaders
- **발표 학회:** NDSS Symposium 2025
- **연구 분야:** 임베디드 보안, 부트로더, 메모리 취약점 분석
- **논문 원문:** [논문 링크](https://www.ndss-symposium.org/wp-content/uploads/2025-330-paper.pdf)

임베디드 보안에 관심을 가지면서 ARM 어셈블리와 메모리 구조를 공부하고 있다. 그 과정에서 운영체제가 실행되기 이전에는 어떤 보안 취약점이 발생할 수 있는지 궁금해졌다. 이번 논문은 부트로더의 메모리 취약점을 체계적으로 분석하고 이를 탐지하는 방법을 제안한다는 점에서 관심 분야와 관련이 있어 선정하였다.

## 2. 연구 배경 및 문제의식
### 주요개념
Firmware는 하드웨어의 동작을 제어하는 소프트웨어  
Bootloader는 시스템의 부팅 과정에서 운영체제를 메모리에 적재하고 실행하는 역할을 하는 프로그램  
대표적인 부트로더로는 GRUB, U-Boot, barebox 등이 있음.  
시스템의 기본적인 부팅 과정은 전원 공급 → 펌웨어 실행 → 부트로더 실행 → 운영체제 실행 순  

### 연구 배경
현대 시스템에서는 신뢰할 수 있는 소프트웨어만 실행하도록 검증하는 Secure Boot라는 보안 기술을 사용하기도 한다. 하지만 이러한 검증 과정에 참여하는 부트로더 자체에 취약점이 존재한다면 시스템 전체의 보안이 위협받을 수 있다.

최근 부트로더는 단순히 운영체제를 실행하는 것뿐만 아니라 파일 시스템 접근, 네트워크 통신, 명령어 처리 등 다양한 기능을 제공한다. 이에 따라 공격자가 접근할 수 있는 영역인 공격 표면(Attack Surface)도 증가하고 있다.

특히 메모리 안전성 문제가 발생하면 프로그램이 할당된 메모리 범위를 벗어나 데이터를 읽거나 쓸 수 있다. 이러한 취약점은 시스템 충돌이나 Secure Boot 우회로 이어질 수 있다.

그러나 기존 연구는 특정 부트로더 또는 일부 입력 처리 기능에 집중되어 있었다. 또한 부트로더는 일반적인 운영체제의 지원 없이 실행되기 때문에 기존 취약점 분석 도구를 그대로 적용하기 어렵다는 문제가 있었다.

## 3. 핵심 아이디어 및 연구 방법

연구진은 기존 부트로더 관련 CVE 85개를 조사하여 주요 공격 표면을 분석하였다.

| 공격 표면 | 주요 입력 | 기존 CVE 수 |
|---|---|---:|
| Storage | 파일 시스템, 저장장치 데이터 | 41 |
| Network | 네트워크 패킷 | 24 |
| Console | 사용자 명령어 | 12 |
| 기타 | 그 외 입력 및 발생 조건 | 8 |

분석 결과 대부분의 취약점이 저장장치, 네트워크, 콘솔을 통해 전달되는 외부 입력과 관련되어 있었다. 이를 바탕으로 연구진은 세 가지 주요 입력 경로를 집중적으로 분석하는 퍼징 프레임워크를 개발하였다.

### 하이퍼바이저 기반 퍼징

퍼징(Fuzzing)은 프로그램에 다양한 입력값을 반복적으로 제공하여 비정상적인 동작이나 취약점을 발견하는 기법이다.

그러나 부트로더는 운영체제 없이 실행되는 Bare Metal 환경에서 동작하기 때문에 AFL, libFuzzer와 같은 기존 퍼징 도구를 그대로 사용하기 어렵다. 부트로더를 일반 프로그램으로 변환하여 분석할 수도 있지만 실제 부팅 환경과의 차이로 인해 발견한 오류가 재현되지 않을 수 있다.

이를 해결하기 위해 연구진은 하이퍼바이저(Hypervisor)를 기반으로 가상머신 실행 환경을 구성하였다.

하이퍼바이저는 가상머신의 CPU, 메모리, 주변장치 등의 자원을 관리하는 소프트웨어이다. 이를 이용하면 실제 부트로더의 실행 환경에 가까운 상태에서 반복적으로 테스트할 수 있으며, 환경 차이로 인해 발생하는 오탐을 줄일 수 있다.

### Test Harness와 Intel PT

Test Harness는 분석하려는 기능을 실행하고 테스트 데이터를 전달하도록 구성한 테스트용 코드이다.

부트로더는 단순히 데이터를 전달하는 것만으로 원하는 기능이 실행되지 않을 수 있다. 예를 들어 파일 시스템을 분석하려면 파일을 읽는 동작을 실행하는 동시에 저장장치에서 읽어오는 데이터를 퍼징 입력으로 바꿔야 한다.

연구진은 이러한 특성을 고려하여 저장장치, 네트워크, 콘솔의 입력 처리 과정을 테스트할 수 있도록 Harness를 구성하였다.

또한 Intel PT(Processor Trace)를 활용하여 CPU가 실행한 코드의 흐름을 추적하였다. 새로운 입력값이 이전에 실행되지 않았던 코드 영역을 실행하게 만드는지 확인하고, 이러한 정보를 퍼징에 활용하여 더 다양한 코드 경로를 탐색할 수 있도록 하였다.

### Heap Sanitizer

일반적인 퍼징에서는 프로그램의 충돌 여부를 통해 취약점을 발견할 수 있다. 그러나 부트로더는 메모리 보호 기능이 제한적인 경우가 있어 잘못된 메모리 접근이 발생하더라도 프로그램이 즉시 종료되지 않을 수 있다.

연구진은 이러한 오류를 탐지하기 위해 부트로더 환경에 맞는 Heap Sanitizer를 구현하였다.

Heap Overflow는 동적으로 할당된 힙 메모리의 범위를 넘어 데이터를 쓰는 취약점이다. 연구진은 메모리 할당 영역 뒤에 8바이트의 추가 공간을 확보하고 특정 값(Magic Number)을 저장하였다.

이후 해당 값의 변경 여부를 검사하여 메모리 영역을 벗어난 쓰기가 발생했는지 확인한다.

이러한 방식은 프로그램의 충돌 여부에만 의존하지 않고 메모리 손상을 직접 검사한다는 점에서 의미가 있다.

## 4. 실험 결과 및 한계

연구진은 GRUB, U-Boot, barebox 등을 포함한 9개의 부트로더를 대상으로 퍼징을 수행하였다.

| 평가 항목 | 결과 |
|---|---:|
| 분석 대상 부트로더 | 9개 |
| 발견한 취약점 | 39개 |
| 새롭게 발견한 취약점 | 38개 |
| 개발자가 확인하거나 패치한 신규 취약점 | 29개 |
| 부여된 CVE 번호 | 5개 |

특히 널리 사용되는 GRUB에서는 14개의 취약점이 발견되었으며 일부는 Secure Boot 우회로 이어질 가능성이 있는 것으로 분석되었다.

### 실제 취약점 사례: barebox Heap Overflow

연구진은 제안한 퍼징 프레임워크를 통해 barebox의 네트워크 패킷 처리 과정에서 Heap Overflow 취약점을 발견하였다.

취약점의 핵심 코드를 단순화하면 다음과 같다.

```c
packet = net_alloc_packet();

if (!packet)
    return 0;

memcpy(packet, pkt, ETHER_HDR_SIZE + len);
```

`net_alloc_packet()`은 1536바이트의 메모리를 할당하지만 이후 `memcpy()`를 실행할 때 복사할 데이터가 해당 크기를 초과하는지 검사하지 않는다.

이 사례는 연구진이 설계한 퍼징 프레임워크가 실제 부트로더의 입력 처리 과정에서 발생하는 메모리 안전성 문제를 발견할 수 있음을 보여준다.

### 연구의 한계

제안된 퍼징 방식은 기존 정적 분석 도구보다 많은 실제 취약점을 발견했지만 정적 분석 도구가 발견한 일부 취약점을 놓치기도 하였다. 따라서 두 가지 분석 방법을 함께 활용하는 것이 효과적일 수 있다고 생각한다.

또한 하드웨어 의존성이 높은 장치 드라이버에 대한 분석이 제한적이며 Heap Sanitizer는 메모리 범위를 벗어난 읽기 오류를 탐지하지 못한다. 새로운 부트로더를 분석할 때 별도의 Test Harness 구현이 필요하다는 점에서도 한계가 존재한다.

특히 다양한 아키텍처와 주변장치를 사용하는 임베디드 시스템의 특성을 고려하면 ARM 기반 환경에서도 분석 방법의 효과를 검증할 필요가 있다고 생각한다.

## 5. 느낀 점 및 향후 계획

이번 논문을 통해 운영체제가 실행되기 이전에도 외부 입력을 처리하는 과정에서 다양한 보안 취약점이 발생할 수 있다는 것을 알게 되었다.

특히 취약점을 효율적으로 발견하기 위해서는 분석 도구를 사용하는 것뿐만 아니라 분석 대상의 실행 환경과 입력 처리 구조를 이해하는 것이 중요하다고 느꼈다.

향수 계획은 다음과 같다.

- **후속 논문:** NDSS 2025에서 발표된 *FUZZUER: Enabling Fuzzing of UEFI Interfaces on EDK-2*를 읽고 부트로더와 UEFI 펌웨어의 퍼징 방법을 비교
- **직접 실습:** QEMU 환경에서 U-Boot를 실행하여 부팅 과정을 확인하고 논문의 Magic Number 기반 메모리 오류 탐지 방식을 간단한 C 프로그램으로 구현해 AddressSanitizer와 비교
- **다른 분야 적용:** 저장장치, 네트워크, 콘솔 입력을 중심으로 분석하는 방식을 IoT 기기나 자동차 제어 장치의 펌웨어 보안에도 적용
- **프로젝트 확장:** 장기적으로는 ARM 기반 임베디드 소프트웨어를 대상으로 외부 입력에 의해 발생하는 메모리 취약점을 자동으로 탐지하는 프로젝트를 진행
