## 1. OWASP Top 10이란?

OWASP(Open Worldwide Application Security Project)는 소프트웨어 및 애플리케이션의 보안 향상을 목적으로 활동하는 비영리 단체이며 OWASP Top 10은 웹 애플리케이션에서 중요하게 다루어야 하는 보안 위험을 10개의 항목으로 분류한 자료를 말한다. 개발자와 보안 담당자가 주요 보안 위험을 파악하고 이를 예방할 수 있도록 도움을 주는 것을 목표로 한다.

OWASP Top 10 중 하나인 Broken Access Control에 대해 공부해보겠다.

## 2. Broken Access Control 보안 동향

Broken Access Control은 2021년과 2025년 모두 OWASP Top 10에서 1위를 차지하였다.

OWASP Top 10 2025에서 발표한 관련 통계는 다음과 같다.

| 항목 | 수치 |
| --- | --- |
| 관련 CWE 개수 | 40개 |
| 평균 취약점 발생률 | 3.74% |
| 총 취약점 발생 건수 | 1,839,701건 |
| 관련 CVE 건수 | 32,654건 |

CWE(Common Weakness Enumeration)는 소프트웨어와 하드웨어에서 발생할 수 있는 보안 약점의 유형을 분류한 것이다.

CVE(Common Vulnerabilities and Exposures)는 공개적으로 알려진 개별 보안 취약점에 식별 번호를 부여하는 체계이다.

위 수치는 OWASP가 분류하고 집계한 자료를 기반으로 하며 실제 해킹 사고의 건수를 의미하는 것은 아니다.

2025년에도 접근 통제 실패가 1위를 유지하고 있다는 점에서 여전히 중요하게 다루어야 하는 보안 문제임을 알 수 있다.

## 3. Broken Access Control이란?

Broken Access Control은 접근 통제 실패를 의미한다.

접근 통제는 사용자가 허용된 범위 내에서만 정보에 접근하거나 특정 기능을 사용할 수 있도록 제한하는 것이다.

예를 들어 병원 예약 시스템에서는 환자와 의료진이 사용할 수 있는 기능이 서로 다르다.

- 환자: 자신의 진료 예약 내역 확인 및 변경
- 의료진: 담당 환자의 진료 정보 확인
- 관리자: 시스템 및 사용자 계정 관리

각 사용자는 자신의 권한에 해당하는 기능만 사용할 수 있어야 한다.

하지만 서버에서 사용자의 권한을 제대로 검증하지 않는다면 환자가 다른 환자의 개인정보를 확인하거나 관리자만 사용할 수 있는 기능에 접근하는 문제가 발생할 수 있다.

이처럼 사용자가 자신의 권한을 벗어나 정보에 접근하거나 기능을 실행할 수 있는 취약점을 Broken Access Control이라고 한다.

## 4. 인증과 인가의 차이

접근 통제를 이해하기 위해서는 인증과 인가의 차이를 먼저 알아야 한다.

### 4.1. 인증(Authentication)

사용자가 누구인지 확인하는 과정이다.

대표적으로 아이디와 비밀번호를 입력하여 본인임을 확인하는 로그인 과정이 해당한다.

### 4.2. 인가(Authorization)

인증된 사용자가 특정 정보에 접근하거나 기능을 실행할 권한이 있는지 판단하는 과정이다.

로그인에 성공하였더라도 모든 정보에 접근할 수 있는 것은 아니므로 별도의 권한 확인이 필요하다.

| 구분 | 인증 | 인가 |
| --- | --- | --- |
| 영어 | Authentication | Authorization |
| 목적 | 사용자 신원 확인 | 사용자 권한 확인 |
| 확인 내용 | 누구인가? | 무엇을 할 수 있는가? |
| 예시 | 로그인 | 관리자 기능 접근 허용 |
| OWASP 2025 관련 항목 | A07: Authentication Failures | A01: Broken Access Control |

인증과 인가는 서로 다른 역할을 수행하며 안전한 시스템을 구성하기 위해서는 두 과정이 모두 정상적으로 이루어져야 한다.

## 5. 접근 통제 실패의 주요 유형

### 5.1. 수평적 권한 상승(Horizontal Privilege Escalation)

동일한 권한 수준을 가진 다른 사용자의 정보나 기능에 접근하는 경우이다.

예를 들어 환자 A와 환자 B는 모두 일반 사용자라는 동일한 권한을 가지고 있다.

그러나 환자 A는 자신의 진료 내역만 확인할 수 있어야 하며 환자 B의 진료 내역에는 접근할 수 없어야 한다.

만약 환자 A가 환자 B의 진료 내역을 조회할 수 있다면 수평적 권한 상승에 해당한다.

```text
환자 A ── 접근 허용 ── 환자 A의 진료 내역
환자 B ── 접근 허용 ── 환자 B의 진료 내역

환자 A ── 비인가 접근 ── 환자 B의 진료 내역
```

사용자의 권한 등급은 동일하지만 접근할 수 있는 정보의 범위를 벗어났다는 점이 특징이다.

### 5.2. 수직적 권한 상승(Vertical Privilege Escalation)

자신보다 높은 권한을 가진 사용자의 기능에 접근하는 경우이다.

예를 들어 일반 사용자가 관리자만 사용할 수 있는 계정 관리 기능이나 시스템 설정 기능을 실행하는 경우이다.

```text
관리자
  ↑
일반 사용자가 관리자 기능에 접근
  ↑
일반 사용자
```

수직적 권한 상승이 발생하면 일반 사용자가 수행할 수 없었던 중요한 기능까지 실행할 수 있어 피해 범위가 커질 수 있다.

### 5.3. 수평적 권한 상승과 수직적 권한 상승 비교

| 구분 | 수평적 권한 상승 | 수직적 권한 상승 |
| --- | --- | --- |
| 권한 수준 | 동일한 권한 | 더 높은 권한 |
| 접근 대상 | 다른 사용자의 정보 | 상위 권한의 기능 |
| 대표적인 피해 | 타인의 개인정보 유출 | 관리자 기능 악용 |

## 6. IDOR(Insecure Direct Object Reference)

### 6.1. IDOR의 개념

IDOR는 안전하지 않은 직접 객체 참조를 의미한다.

웹 애플리케이션에서는 사용자 정보, 문서, 예약 내역 등의 데이터를 구분하기 위해 고유한 식별자를 사용한다.

서버가 해당 식별자로 데이터를 조회하면서 요청한 사용자에게 접근 권한이 있는지 확인하지 않으면 IDOR 취약점이 발생할 수 있다.

### 6.2. IDOR 발생 원리

가상의 도서관 시스템에서 사용자가 자신의 도서 대출 내역을 조회한다고 가정해 보자.

서버는 대출 내역의 고유한 번호를 이용하여 데이터베이스에서 해당 정보를 조회한다.

| 대출 번호 | 소유자 |
| --- | --- |
| 101 | 사용자 A |
| 102 | 사용자 B |
| 103 | 사용자 C |

사용자 A는 자신의 대출 내역인 101번에만 접근할 수 있어야 한다.

하지만 서버가 요청받은 대출 번호만 확인하고 실제 소유자가 누구인지 검증하지 않는다면 다른 사용자의 대출 내역에도 접근할 수 있게 된다.

정상적인 접근 과정은 다음과 같다.

```text
대출 내역 조회 요청
        ↓
로그인 상태 확인
        ↓
대출 내역 조회 권한 확인
        ↓
권한이 있는 경우에만 정보 반환
```

반면 취약한 시스템에서는 다음과 같이 동작할 수 있다.

```text
대출 내역 조회 요청
        ↓
로그인 상태 확인
        ↓
대출 번호로 데이터 조회
        ↓
소유자 확인 없이 정보 반환
```

IDOR의 근본적인 원인은 식별자를 외부에서 확인하거나 변경할 수 있다는 사실 자체가 아니라 해당 데이터에 대한 접근 권한을 검증하지 않는다는 점이다.

IDOR는 수평적 권한 상승을 발생시키는 대표적인 취약점이며 경우에 따라 수직적 권한 상승으로 이어질 수도 있다.

## 7. 취약점 발생 원인

### 7.1. 서버 측 권한 검증 누락

사용자가 로그인하였는지만 확인하고 요청한 정보나 기능에 접근할 권한이 있는지는 확인하지 않는 경우이다.

이러한 권한 검증 누락은 CWE-862(Missing Authorization)와 관련된다.

### 7.2. 클라이언트 측에서만 권한 확인

일반 사용자의 화면에서 관리자 메뉴를 숨기는 것만으로는 접근 통제가 이루어졌다고 볼 수 없다.

클라이언트는 사용자가 직접 제어할 수 있는 영역이므로 서버에서도 실제 접근 권한을 검증해야 한다.

화면에 특정 기능이 보이지 않는 것과 해당 기능에 접근할 수 없는 것은 서로 다른 문제이다.

### 7.3. 사용자 입력값에 대한 과도한 신뢰

사용자가 전달한 식별자나 권한 정보를 별도의 검증 없이 신뢰하는 경우이다.

서버는 클라이언트에서 전달받은 정보만으로 사용자의 권한을 결정해서는 안 된다.

서버에서 검증한 사용자 정보와 실제 권한을 기반으로 접근 가능 여부를 판단해야 한다.

이러한 유형의 취약점은 CWE-639(Authorization Bypass Through User-Controlled Key)와 관련된다.

### 7.4. 과도한 권한 부여

사용자가 실제로 필요한 범위보다 많은 권한을 가지고 있는 경우이다.

불필요한 권한이 부여되어 있으면 정상적으로 로그인한 사용자도 자신에게 필요하지 않은 정보와 기능에 접근할 수 있다.

## 8. 취약한 코드와 개선된 코드 비교

아래 코드는 실제 서비스가 아닌 접근 통제 실패의 원리를 설명하기 위한 가상의 Python 코드이다.

### 8.1. 취약한 코드

```python
def view_document(document_id, current_user):
    if current_user is None:
        return "로그인이 필요합니다."

    document = find_document(document_id)

    return document
```

위 코드에서는 사용자의 로그인 여부만 확인한다.

요청한 문서가 실제로 해당 사용자의 문서인지 확인하지 않기 때문에 다른 사용자의 문서가 반환될 가능성이 있다.

### 8.2. 개선된 코드

```python
def view_document(document_id, current_user):
    if current_user is None:
        return "로그인이 필요합니다."

    document = find_document(document_id)

    if document is None:
        return "문서가 존재하지 않습니다."

    if document.owner_id != current_user.id:
        return "접근 권한이 없습니다."

    return document
```

개선된 코드에서는 문서의 소유자와 현재 로그인한 사용자가 일치하는지 확인한다.

해당 문서에 접근할 권한이 없는 사용자의 요청을 거부함으로써 다른 사용자의 문서가 노출되는 것을 방지할 수 있다.

이 예시는 문서 소유자만 접근할 수 있는 서비스를 가정한 것이며 실제 서비스에서는 공유 권한이나 관리자 권한 등을 추가적으로 고려해야 한다.

## 9. 발생 가능한 피해

접근 통제 실패가 발생하면 다음과 같은 피해로 이어질 수 있다.

- 타인의 개인정보 및 민감한 정보 유출
- 다른 사용자의 데이터 수정 및 삭제
- 관리자 기능에 대한 비인가 접근
- 사용자 계정 및 권한 관련 정보 변경
- 서비스 운영에 영향을 주는 기능의 악용

실제 피해 범위는 접근할 수 있는 정보와 기능에 따라 달라진다.

## 10. 예방 및 대응 방법

### 10.1. 서버 측 접근 권한 검증

사용자가 특정 정보나 기능에 접근할 때 서버에서 실제 권한을 검증해야 한다.

로그인 여부뿐만 아니라 요청한 자원에 접근할 권한이 있는지도 함께 확인해야 한다.

### 10.2. 최소 권한 원칙(Least Privilege)

사용자에게 자신의 역할과 기능을 수행하는 데 필요한 최소한의 권한만 부여하는 원칙이다.

불필요한 권한을 제거함으로써 허용되지 않은 정보나 기능에 접근할 가능성을 줄일 수 있다.

### 10.3. 기본 거부 원칙(Deny by Default)

명시적으로 허용된 접근을 제외하고는 기본적으로 모든 접근을 거부하는 방식이다.

권한이 명확하게 확인되지 않은 경우에는 접근을 허용하지 않아야 한다.

### 10.4. 역할 기반 접근 통제(RBAC)

RBAC(Role-Based Access Control)는 사용자의 역할에 따라 접근 권한을 부여하는 방식이다.

| 역할 | 허용되는 기능 |
| --- | --- |
| 일반 사용자 | 일반 기능 이용 |
| 담당자 | 담당 업무 관리 |
| 관리자 | 시스템 관리 |

사용자별로 모든 권한을 개별적으로 설정하는 대신 역할에 따라 권한을 관리할 수 있다.

다만 동일한 역할을 가진 사용자들 사이에서도 접근할 수 있는 데이터가 다를 수 있기 때문에 RBAC만으로 모든 접근 통제 문제를 해결할 수 있는 것은 아니다.

### 10.5. 객체 단위 접근 권한 검증

문서, 계정, 예약 내역 등 개별 데이터에 접근할 때마다 해당 사용자에게 접근 권한이 있는지 확인해야 한다.

식별자를 예측하기 어려운 값으로 변경하는 것은 추가적인 보호 수단이 될 수 있지만 권한 검증 자체를 대신할 수는 없다.

### 10.6. 보안 테스트 및 로그 기록

서로 다른 권한을 가진 계정으로 기능을 테스트하여 접근 통제가 제대로 이루어지는지 확인해야 한다.

또한 권한이 없는 사용자의 접근 시도를 로그로 기록하고 반복적으로 발생하는 비정상적인 요청을 확인할 필요가 있다.

## 11. 시스템 해킹과의 연관성

접근 권한은 웹 애플리케이션뿐만 아니라 운영체제에서도 중요하게 다루어지는 개념이다.

운영체제에서도 일반 사용자와 관리자에게 서로 다른 권한을 부여하며 파일, 디렉터리, 프로그램 등에 대한 접근을 제한한다.

시스템 해킹에서는 취약점을 이용하여 일반 사용자 권한에서 관리자 권한으로 상승하는 문제를 다루기도 한다.

웹 애플리케이션의 권한 상승과 운영체제의 권한 상승은 구체적인 발생 원리와 대상이 다를 수 있지만 허용된 권한의 범위를 벗어난다는 공통점이 있다.

따라서 접근 통제에 대한 이해는 웹 해킹뿐만 아니라 시스템 보안을 공부하는 데에도 도움이 된다고 생각한다.

## 12. 학습을 통해 알게 된 점

이전에 WebGoat과 Burp Suite를 활용하여 웹 해킹을 공부하면서 HTTP 요청을 변경하여 인증 절차를 우회하는 실습을 진행한 경험이 있다.

당시에는 인증 우회와 접근 통제 실패의 차이에 대해 깊이 생각하지 않았지만 이번 학습을 통해 인증과 인가가 서로 다른 역할을 수행한다는 것을 알게 되었다.

특히 로그인한 사용자라고 하더라도 요청하는 정보나 기능마다 접근 권한을 확인해야 한다는 점이 중요하다고 생각하였다.

또한 복잡한 공격 기법이 사용되지 않더라도 개발 과정에서 권한 검증이 누락되는 것만으로 심각한 보안 문제가 발생할 수 있다는 것을 알게 되었다.

앞으로 웹 해킹이나 시스템 해킹을 공부할 때 기능의 동작 방식뿐만 아니라 해당 기능이 어떤 권한으로 실행되는지에도 주의를 기울이고자 한다.
