## 1. Fuzzing이란?

퍼징(Fuzzing)은 프로그램에 다양한 입력값을 반복적으로 전달하여 오류나 비정상적인 동작을 발견하는 소프트웨어 테스트 기법이다.

프로그램을 개발할 때 모든 입력값에 대해 정상적으로 동작하는지 확인하는 것은 어렵다. 특히 개발자가 예상하지 못한 입력값이 전달되면 프로그램이 비정상적으로 종료되거나 보안 취약점이 발생할 수 있다.

퍼징은 이러한 입력값을 자동으로 생성하고 테스트함으로써 사람이 직접 발견하기 어려운 오류와 취약점을 찾아내는 데 사용된다.

### 1.1. Fuzzing과 Fuzzer의 차이

| 구분 | 설명 |
| --- | --- |
| Fuzzing(퍼징) | 다양한 입력값을 통해 오류나 취약점을 발견하는 테스트 기법 |
| Fuzzer(퍼저) | 퍼징을 자동으로 수행하는 도구 |

즉, Fuzzing은 테스트 방법을 의미하고 Fuzzer는 해당 방법을 수행하는 도구를 의미한다.

## 2. Fuzzing의 동작 원리

퍼징은 일반적으로 다음과 같은 과정을 반복하며 수행된다.

1. 테스트 대상 프로그램을 선정한다.
2. 다양한 입력값을 생성하거나 기존 입력값을 변형한다.
3. 생성된 입력값을 프로그램에 전달한다.
4. 프로그램의 실행 결과를 확인한다.
5. 오류나 충돌이 발생한 입력값을 저장하고 분석한다.

예를 들어 문자열을 입력받는 프로그램을 테스트한다고 가정해 보자.

| 입력값 | 예상 실행 결과 |
| --- | --- |
| hello | 정상 실행 |
| 12345 | 정상 실행 |
| !@#$% | 정상 실행 |
| 빈 문자열 | 오류 발생 |
| 매우 긴 문자열 | 프로그램 충돌 |

위와 같이 특정 입력값에서 문제가 발생한다면 해당 입력값을 다시 사용하여 오류의 원인을 분석할 수 있다.

퍼저에 따라 프로그램에서 이전에 실행되지 않았던 코드 영역을 확인하고 이를 바탕으로 새로운 입력값을 생성하기도 한다.

이때 프로그램의 코드가 어느 정도 실행되었는지를 나타내는 정보를 코드 커버리지(Code Coverage)라고 한다.

## 3. Fuzzing의 종류

퍼징은 프로그램의 내부 정보를 얼마나 활용하는지와 입력값을 어떻게 생성하는지에 따라 분류할 수 있다.

### 3.1. 프로그램 내부 정보 활용 여부에 따른 분류

#### Black-box Fuzzing

프로그램의 내부 구조를 알지 못하는 상태에서 입력값과 실행 결과를 중심으로 테스트하는 방식이다.

소스코드가 제공되지 않는 프로그램에도 적용하기 쉽지만 프로그램 내부의 어떤 코드가 실행되었는지 알기 어려워 복잡한 실행 경로를 탐색하는 데 한계가 있다.

#### White-box Fuzzing

프로그램의 내부 구조와 실행 조건 등을 분석하여 입력값을 생성하는 방식이다.

프로그램 내부의 복잡한 조건을 만족하는 입력값을 생성할 수 있지만 분석 과정에서 많은 시간과 연산 자원이 필요할 수 있다.

#### Grey-box Fuzzing

프로그램의 모든 내부 구조를 분석하지는 않지만 코드 커버리지와 같은 일부 실행 정보를 활용하는 방식이다.

실행 결과를 바탕으로 새로운 코드 영역을 탐색할 수 있도록 입력값을 생성한다.

| 구분 | 내부 정보 활용 | 특징 |
| --- | --- | --- |
| Black-box | 활용하지 않음 | 비교적 적용하기 쉬움 |
| White-box | 상세하게 활용 | 복잡한 실행 조건 분석 가능 |
| Grey-box | 일부 활용 | 실행 정보를 바탕으로 효율적인 탐색 가능 |

### 3.2. 입력값 생성 방식에 따른 분류

#### Mutation-based Fuzzing

기존에 존재하는 입력값을 변형하여 새로운 입력값을 생성하는 방식이다.

예를 들어 기존 문자열이 ABCD라면 일부 문자를 변경하거나 추가, 삭제하여 새로운 입력값을 만든다.

- ABCD → ABXD
- ABCD → ABCDDD
- ABCD → ABD

기존 입력값을 활용하기 때문에 비교적 쉽게 테스트를 시작할 수 있지만 초기 입력값의 구성에 따라 테스트 효율이 달라질 수 있다.

#### Generation-based Fuzzing

입력 데이터의 형식이나 구조, 규칙 등을 기반으로 새로운 입력값을 생성하는 방식이다.

특정 파일 형식이나 네트워크 프로토콜처럼 정해진 규칙이 존재하는 대상을 테스트할 때 활용할 수 있다.

| 구분 | 입력값 생성 방식 |
| --- | --- |
| Mutation-based | 기존 입력값을 변형 |
| Generation-based | 데이터의 형식이나 규칙을 기반으로 생성 |

두 분류 기준은 서로 독립적이다. 따라서 Grey-box Fuzzing에서도 Mutation-based 방식이나 Generation-based 방식을 활용할 수 있다.

## 4. 대표적인 Fuzzer

### 4.1. AFL++

AFL++은 기존 AFL(American Fuzzy Lop)을 기반으로 여러 기능과 성능을 개선한 오픈소스 퍼저이다.

프로그램의 실행 정보를 활용하여 새로운 코드 영역을 탐색하고 기존 입력값을 변형하면서 테스트를 반복한다.

주요 특징은 다음과 같다.

- 코드 커버리지 기반 퍼징
- 다양한 입력값 변형 방식 지원
- 여러 계측 방식 지원
- 소스코드가 없는 바이너리도 지원되는 실행 모드를 통해 테스트 가능

다양한 환경에서 프로그램의 오류와 메모리 관련 취약점을 발견하는 데 활용할 수 있다.

### 4.2. Jackalope

Jackalope는 Google Project Zero에서 개발한 바이너리 기반의 코드 커버리지 퍼저이다.

바이너리 계측을 통해 프로그램의 실행 정보를 수집할 수 있으며 Windows, macOS, Linux, Android 환경을 지원한다.

주요 특징은 다음과 같다.

- 바이너리 기반 퍼징
- 코드 커버리지 활용
- 다양한 운영체제 지원
- TinyInst를 이용한 동적 바이너리 계측 지원

특히 소스코드를 확보하기 어려운 바이너리 프로그램을 분석할 때 활용할 수 있다는 특징이 있다.

### 4.3. libFuzzer

libFuzzer는 LLVM 기반의 코드 커버리지 퍼저로 프로그램 전체보다는 특정 함수나 라이브러리를 대상으로 테스트할 때 주로 사용된다.

테스트 대상에 입력값을 전달하는 함수를 작성하고 동일한 프로세스 안에서 해당 함수를 반복적으로 실행한다.

주요 특징은 다음과 같다.

- 함수 및 라이브러리 단위의 퍼징
- 코드 커버리지 활용
- LLVM 기반의 계측
- AddressSanitizer 등의 오류 탐지 도구와 함께 사용 가능

특정 함수나 라이브러리에서 발생하는 메모리 접근 오류 등을 발견하는 데 활용할 수 있다.

## 5. Fuzzer별 차이점

| 구분 | AFL++ | Jackalope | libFuzzer |
| --- | --- | --- | --- |
| 주요 테스트 대상 | 범용 프로그램 | 바이너리 프로그램 | 함수 및 라이브러리 |
| 코드 커버리지 활용 | O | O | O |
| 소스코드 필요 여부 | 실행 모드에 따라 다름 | 바이너리 계측 시 불필요 | 일반적으로 필요 |
| 주요 특징 | 다양한 계측 및 퍼징 방식 지원 | 동적 바이너리 계측 및 여러 운영체제 지원 | 동일 프로세스 내에서 함수 반복 실행 |

세 가지 도구 모두 코드 커버리지를 활용하지만 테스트 대상과 실행 정보를 수집하는 방식에서 차이가 있다.

AFL++은 다양한 프로그램을 테스트하기 위한 범용적인 도구로 활용할 수 있으며 Jackalope는 바이너리 프로그램을 분석하는 데 적합하다.

libFuzzer는 특정 함수나 라이브러리를 집중적으로 테스트할 때 활용할 수 있다.

따라서 테스트하려는 프로그램의 특성과 소스코드 확보 여부 등을 고려하여 적절한 퍼저를 선택하는 것이 중요하다.

## 6. Fuzzing으로 발견할 수 있는 취약점

| 취약점 및 오류 | 설명 |
| --- | --- |
| Buffer Overflow | 할당된 버퍼의 크기를 초과하여 데이터를 기록하는 문제 |
| Use-After-Free | 이미 해제된 메모리에 접근하는 문제 |
| Out-of-Bounds Access | 허용된 메모리 범위를 벗어나 접근하는 문제 |
| Integer Overflow | 정수가 표현 가능한 범위를 초과하는 문제 |
| Null Pointer Dereference | 널 포인터가 가리키는 위치에 접근하려는 문제 |

다만 퍼징 과정에서 프로그램이 충돌하거나 오류가 발생하였다고 해서 반드시 보안 취약점이 존재하는 것은 아니다.

발견된 오류가 실제로 보안에 영향을 미치는지 확인하기 위해서는 추가적인 분석이 필요하다.

## 7. Fuzzing의 장단점

### 장점

- 많은 입력값을 자동으로 테스트할 수 있다.
- 개발자가 예상하지 못한 입력값에서 발생하는 오류를 발견할 수 있다.
- 반복적인 테스트에 필요한 시간과 노력을 줄일 수 있다.
- 프로그램 내부에 존재하는 메모리 관련 취약점을 발견하는 데 활용할 수 있다.

### 단점

- 모든 실행 경로와 취약점을 발견할 수 있는 것은 아니다.
- 초기 입력값과 퍼징 환경에 따라 테스트 효율이 달라질 수 있다.
- 복잡한 실행 조건을 만족하는 입력값을 생성하기 어려울 수 있다.
- 발견된 오류에 대한 추가적인 분석이 필요하다.

## 8. 학습 소감

퍼징에 대해 공부하면서 다양한 입력값을 자동으로 테스트하는 것뿐만 아니라 프로그램의 실행 정보를 활용하여 테스트의 효율을 높일 수 있다는 것을 알게 되었다.

특히 같은 목적을 가진 퍼저라도 테스트 대상과 실행 방식에 따라 서로 다른 특징을 가진다는 점이 인상적이었다.

퍼징을 통해 취약점이 발생할 가능성이 있는 부분을 발견할 수 있지만 실제 보안 취약점인지 판단하기 위해서는 프로그램의 동작 원리와 오류의 발생 원인을 분석하는 능력도 필요하다고 생각한다.

이후에는 실제 퍼저를 사용하여 프로그램을 테스트하고 발견된 오류를 분석해 보고 싶다.
